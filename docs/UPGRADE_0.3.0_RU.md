# TeamTrackerGTNH 0.3.0 — безопасность обновления

## Короткий вывод

Обновление с 0.2.2 или 0.2.3 на 0.3.0 не требует миграции мира или удаления
конфига. Поддерживаемая операция — полностью остановить сервер/клиент, удалить
старый JAR, положить новый JAR и запустить процесс снова. Hot-swap JAR в уже
работающей JVM Forge 1.7.10 не поддерживается.

## Почему мир не должен сломаться

Мод не регистрирует и не сохраняет:

- блоки, предметы, сущности, tile entities или измерения;
- numeric registry IDs;
- `WorldSavedData`, capability или player/world NBT;
- команды/объекты, которые должны быть восстановлены из сейва.

Серверное состояние — это временный снимок онлайн-игроков одной команды. После
перезапуска он заново строится из ServerUtilities. Удаление/замена JAR поэтому не
оставляет missing mappings и не изменяет файлы мира.

## Конфиг

0.3.0 добавляет `internal.schemaVersion=1` и сохраняет все имена, значения и
дефолты ключей 0.2.x. Миграция 0 → 1 метадатная: пользовательские настройки не
перезаписываются. Неизвестные свойства и категории Forge Configuration сохраняет,
что позволяет будущим версиям добавлять настройки без очистки cfg.

Если cfg создан более новой версией, 0.3.0 читает известные ключи, пишет
предупреждение и не понижает номер схемы.

## Сеть и порядок замены JAR

Сохранены без изменений:

- channel: `teamtrackergtnh`;
- discriminator: `0`;
- 0.2.x prefix пакета: count, UUID, name, dimension, X/Y/Z.

После последнего legacy-entry 0.3.0 может добавить envelope
`magic + version + length + payload`. Старый клиент читает привычный prefix и
игнорирует хвост. Новый клиент принимает и пакет 0.2.x без envelope.

Envelope v1 хранит монотонный номер полного snapshot. Клиент не применяет
повторный/запоздавший пакет и не разрешает legacy-пакету откатить уже sequenced
сессию. На connect/disconnect номер сбрасывается вместе с session generation.

0.3.0 объявляет Forge-диапазон remote wire-совместимости `[0.2.2,0.4.0)`.
Однако старые 0.2.x JAR не объявляли свой диапазон, а пустое значение FML
трактует как «только точно эта версия». Поэтому первый переход 0.2.x → 0.3.0
нужно выполнить одновременно на сервере и всех клиентах: старый участник может
отклонить новую версию на handshake ещё до чтения совместимого пакета.

Явный диапазон в 0.3.0 подготавливает поэтапную замену будущих совместимых
0.3.x JAR. Версия `0.2.1-test` не входит в диапазон.

## Порядок обновления

1. Сделать обычный backup мира и cfg.
2. Остановить dedicated server и дождаться завершения JVM.
3. Удалить только старый `teamtrackergtnh-*.jar`.
4. Положить `teamtrackergtnh-0.3.0.jar`; рядом не должно быть второй версии.
5. На клиентах при закрытом Minecraft так же заменить JAR.
6. Запустить сервер, затем клиенты; существующие world/cfg оставить на месте.
7. Проверить отсутствие network decode/FML handshake ошибок и появление teammate
   markers после входа двух игроков в одну ServerUtilities-команду.

## Границы гарантии

Статическая и протокольная проверка не заменяет реальный тест на dedicated
server с двумя клиентами. Для релиза проверены обе стороны wire-совместимости и
порядок snapshot, но реальный GL/Xaero/Navigator pipeline зависит от конкретной
сборки клиента и должен быть пройден acceptance-тестом.
